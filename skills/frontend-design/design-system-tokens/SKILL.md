# Design System Tokens

Scope: color, type, spacing, radii, shadows, motion, breakpoints and z-index tokens; DTCG 2025.10 JSON source; generated CSS; Tailwind v3/v4 and copy-in component library wiring; contrast checks per theme.

Components consume **semantic** tokens; semantic tokens point at **primitives**; themes swap the semantic mapping. Raw values never appear in components.

## Inputs

| Parameter | Required | Default | Example |
|---|---|---|---|
| `mode` | required | — | `create` (from a direction) · `extract` (from existing code/site) · `wire` (connect existing tokens to framework/components) |
| `source` | required for extract | — | `src/` (stylesheets/components) or a public URL you are allowed to analyse |
| `direction` | optional (create) | design plan if present | palette and type from frontend-visual-direction |
| `themes` | optional | `light`, `dark` | `light,dark,high-contrast` or brands `acme,partner` |
| `targets` | optional | CSS custom properties | Tailwind v4 `@theme`, Tailwind v3 config, JSON for native apps |
| `format` | optional | DTCG-style JSON source + generated CSS | CSS-only for small projects |
| `component_lib` | optional | detected | headless primitives with copied-in components; existing in-house kit |

## Output

- `tokens/tokens.json` (source of truth, DTCG-style) and generated `tokens.css` (and framework theme file if targeted).
- Contrast report for every text/background and UI/background pair in every theme.
- (extract) Consolidation report: clusters found (e.g. 23 greys → 11-step ramp), mapping old → new, and files to update.
- A short `tokens/README.md`: layers, naming, how to add a token, how to theme.

## Supporting files

- [REFERENCE.md](REFERENCE.md): naming rules, layer design, building color ramps, contrast targets, type/spacing/radius/shadow/motion scales, dark-mode mapping, framework wiring (Tailwind v3/v4, CSS-in-JS, native), build pipeline, lint enforcement, and component-library rules. Read at steps 3–6.
- [templates/tokens.json](templates/tokens.json): source-of-truth skeleton with primitives, semantic light/dark, and component tokens.
- [templates/tokens.css](templates/tokens.css): layered custom properties with theme switching via `[data-theme]` and `prefers-color-scheme`.
- [scripts/extract-tokens.py](scripts/extract-tokens.py): scans stylesheets/components, clusters near-duplicate colors (perceptual distance), and lists font families, font sizes, spacing, radii, shadows by frequency. Run in `extract` mode.
- [scripts/contrast-check.py](scripts/contrast-check.py): resolves a tokens.json and checks declared contrast pairs per theme against WCAG targets. Run after any color change. `--pair FG BG` checks one ad hoc pair.
- [scripts/build-css.py](scripts/build-css.py): generates `tokens.css` (primitives, one block per theme, system-dark fallback, component tokens) from tokens.json and fails on unresolved references. The template CSS was generated by it.

## Steps

1. **Inventory**: existing tokens, theme files, framework (and its major version), component library, platforms (web only, or native too). Never overwrite an existing system without confirmation.
2. **Extract** (mode `extract`): `python3 scripts/extract-tokens.py <source> --json > tokens-extract.json`. Review clusters: decide which near-duplicates merge, which are intentional. For a public website, analyse only what you are allowed to, treat one page as partial evidence, and do not copy brand assets.
3. **Design primitives**: neutral ramp (11–12 steps), 1–2 accent ramps, status hues (success, warning, danger, info); type families, a size scale from a ratio; 4 px spacing scale; 3–5 radii; 3 shadow levels; durations and easings; breakpoints; z-index layers.
4. **Map semantics by role**, not appearance: `color.bg`, `color.bg-subtle`, `color.surface`, `color.text`, `color.text-muted`, `color.border`, `color.accent`, `color.accent-text`, `color.focus`, `color.danger`… (dot = group, hyphen = role name, so the CSS variable is `--color-text-muted`). Define every role in every theme; a role missing from one theme is a bug. Keep the semantic set small (aim for 20–40 color roles).
5. **Check contrast**: declare pairs in tokens.json (`text` on `bg`, `text-muted` on `surface`, `accent-text` on `accent`, `border` on `surface` for UI ≥ 3:1) and run `python3 scripts/contrast-check.py tokens/tokens.json`. Fix failing roles by moving to another ramp step, not by adding one-off colors.
6. **Generate outputs** for `targets`: `python3 scripts/build-css.py tokens/tokens.json -o tokens/tokens.css` for CSS variables; framework theme files map onto those variables (REFERENCE.md has the wiring for each). If the project already uses a token build tool, use it instead. Keep generated files marked "do not edit" and regenerate after every tokens.json change.
7. **Wire components**: primitives (button, input, select, checkbox, card, dialog, toast, table) use only semantic/component tokens. Prefer the component library's variants over custom classes; layout classes on components, not color/typography overrides.
8. **Enforce**: add a lint rule that blocks raw hex/rgb and off-scale spacing in components (stylelint or a grep in CI). Replace hard-coded values incrementally, highest-traffic components first.
9. **Document and show**: `tokens/README.md` plus a living page/story that renders every token and component state in each theme.

## Checkpoints

- After step 2: agree which clusters merge before renaming anything.
- After step 5: zero failing contrast pairs (or each exception approved).
- Before step 8 replacements on shared components: visual check in every theme.

## Worked example

Extract on `src/`: script reports 23 distinct greys, 6 blues, 11 font sizes, spacing values 5/6/10/13/15/18 px mixed with the 4 px scale.

Decisions:
- Greys → 11-step neutral ramp `gray.50…gray.950`; `#f3f4f6`, `#f2f3f5`, `#f4f4f5` merge into `gray.100`.
- Blues → `blue.600` primary, `blue.700` hover; others removed.
- Font sizes → 12, 14, 16, 18, 20, 24, 30, 36 (1.2-ish scale, rounded).
- Spacing → 4 px scale; 5→4, 6→8, 10→8 or 12 by context, 13/15→16, 18→16 or 20.

Semantic mapping (light / dark): `color.bg` gray.50 / gray.950; `color.text` gray.900 / gray.50; `color.text-muted` gray.600 / gray.400; `color.accent` blue.600 / blue.400; `color.accent-text` white / gray.950.
Contrast check: `text-muted` on `surface` in dark = 4.1:1 → fails; moved to gray.300 = 6.8:1.
Build: `build-css.py` writes `tokens.css`; `rg -n '#[0-9a-fA-F]{3,8}\b' src/components` lists the 140 raw values left to replace, highest-traffic components first.

## Pitfalls

- Too many tokens nobody can remember; every one-off becomes a token.
- Semantic names that encode a color (`blue-button`) or a component that does not exist.
- Components reaching for primitives directly, breaking theming.
- Dark mode by inverting the ramp; dark needs its own mapping (lighter surfaces for elevation, less saturated accents).
- Overriding component-library colors with utility classes instead of changing tokens.
- Manual `dark:` overrides scattered in components instead of semantic tokens that switch.
- Declaring the system "complete" from one page or partial extraction.

## Done when

- [ ] tokens.json holds primitives, semantic roles per theme, and (only where needed) component tokens.
- [ ] Generated CSS/theme outputs exist and are marked generated.
- [ ] Every declared contrast pair passes in every theme.
- [ ] Core components consume only semantic/component tokens; lint blocks new raw values.
- [ ] README and a token/component showcase page exist.
- [ ] (extract) Consolidation report lists merges and remaining exceptions.
