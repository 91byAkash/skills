## 1. Statistics for conversion tests

### Inputs to every sample-size calculation
- **Baseline rate**: the control rate of the exact metric on the exact page/step, from the last 2-4 comparable weeks. Never a site-wide average.
- **MDE (minimum detectable effect)**: the smallest lift worth acting on. Relative (15% of 4% = 0.6 points) unless stated absolute. Pick from business value: "what lift pays for building and maintaining this?"
- **Alpha** (false-positive rate): 0.05 two-sided by default.
- **Power** (chance to detect a true effect of size MDE): 0.80 default; 0.90 for pricing, checkout, or anything costly to get wrong.

### Formula (two proportions, two-sided)
```
n per arm = [ z(1-α/2)·√(2·p̄·(1-p̄)) + z(1-β)·√(p1(1-p1) + p2(1-p2)) ]² / (p2 - p1)²
p̄ = (p1 + p2)/2      z(0.975) = 1.96      z(0.80) = 0.84      z(0.90) = 1.28
```
Rule of thumb for a sanity check: n ≈ 16·p(1-p)/δ² at α = 0.05, power 0.8 (δ = absolute difference).

### Quick reference (per arm, α 0.05 two-sided, power 0.8; generated by `scripts/abtest.py table`)

| Baseline | 5% lift | 10% lift | 20% lift | 50% lift |
|---|---|---|---|---|
| 1% | 637,010 | 163,095 | 42,693 | 7,750 |
| 2% | 315,206 | 80,682 | 21,109 | 3,826 |
| 3% | 207,938 | 53,211 | 13,914 | 2,518 |
| 5% | 122,124 | 31,234 | 8,158 | 1,471 |
| 10% | 57,763 | 14,751 | 3,841 | 686 |
| 20% | 25,583 | 6,510 | 1,683 | 294 |

Note: many published "quick tables" understate these by 2-4x. Trust the formula.

### Duration
```
days = (n per arm × arms) / (eligible daily visitors × share exposed)
```
Round up to whole weeks. Minimum 7 days (weekday effects); B2B: two business cycles; ecommerce: span a pay cycle (start/end of month). Maximum ~8 weeks: cookies churn, novelty fades, other launches contaminate.

Feasibility bands: < 7 days easy (still run a week); 7-28 feasible; 28-56 only for high-impact; > 56 not feasible.

### When the required sample is too large
1. Test a bolder change (larger MDE).
2. Move upstream where traffic is higher (e.g., click-to-pricing instead of paid conversion), keeping a downstream guardrail.
3. Pool similar pages/templates into one test.
4. Cut to one variant.
5. Accept 90% confidence and document it (higher false-positive risk).
6. Decide with qualitative evidence (user tests, recordings, surveys) and monitor post-launch with a before/after plus holdout if possible.

### Multiple variants
Each extra arm adds sample and comparisons. With k arms compared to control, use α/(k-1) (Bonferroni; `--variants k` does this). Rough totals vs A/B: 3 arms ≈ 1.8x, 4 arms ≈ 2.7x total traffic (with the correction). Beyond 4 arms, cut variants. Multivariate tests need every combination powered; only for very high-traffic pages.

### Reading a result
- **p-value**: probability of a difference at least this large if there were no true difference. It is not "the chance the variant is better".
- **Confidence interval**: the plausible range of the true effect. Decide with it: if the whole CI is above zero and its lower end is commercially meaningful → strong win; if it spans zero → inconclusive; if it excludes meaningful harm → safe to ship a simpler variant.
- **Practical vs statistical significance**: a significant +0.5% relative lift may not justify the maintenance cost.

### Sample ratio mismatch (SRM)
Chi-square on assignment counts vs planned split. p < 0.001 → the experiment is broken (redirect losses in one arm, bot filtering, caching, tracking firing only after variant JS loads). Do not analyze until fixed. `abtest.py srm --counts a b [--split 50 50]`.

### Peeking and sequential testing
Checking a fixed-horizon test daily and stopping at the first p < 0.05 inflates false positives to 20-30%+. If you must monitor for early stopping, pre-register a sequential method (alpha spending such as O'Brien-Fleming boundaries, always-valid/mSPRT p-values, or a Bayesian decision rule with a pre-set loss threshold). They cost roughly 10-30% more sample at the planned horizon. Guardrail-driven stops for harm are always allowed.

### Other traps
- **Novelty/primacy**: returning users react to change itself. If the lift decays week over week, compare new-user-only results.
- **Segment mining**: with 10 segments, one will look significant by chance. Segment results are hypotheses for the next test.
- **Revenue metrics**: heavy-tailed; use revenue per visitor with a winsorized cap (e.g., 99th percentile) or bootstrap CIs. The script handles proportions only.
- **Variance reduction**: pre-period covariate adjustment (CUPED-style) can cut needed sample 20-50% when a strong pre-experiment metric exists; use if the testing tool supports it.
- **Interaction**: concurrent tests on the same page/element must be mutually exclusive; tests on different funnel stages can overlap.

## 2. Test types, allocation and implementation

| Type | What changes | Traffic need | Use when |
|---|---|---|---|
| A/B | One change, two arms | Moderate | Default |
| A/B/n | Several alternatives | Higher | Genuinely different directions, enough traffic |
| Multivariate | Combinations of elements | Very high | Huge traffic, need interaction effects |
| Split URL | Whole different page | Moderate | Redesigns, different templates |
| Holdout | Feature on vs withheld group | Depends | Measuring cumulative impact of lifecycle email, onboarding, ads incrementality |

| Allocation | Use |
|---|---|
| 50/50 | Default |
| 80/20 or 90/10 | Risky change; needs longer run for the same power |
| Ramp 5% → 25% → 50% | Technical risk; analyze only the 50/50 period |

Implementation: client-side tools are quick but can flicker (hurts the variant and leaks the test); use an anti-flicker snippet with a short timeout (≤ 1 s) or server-side/edge assignment. Pricing and checkout tests: server-side only, with consistent assignment across sessions and devices (hash of user id).

What to vary: headline/value angle, information order and amount, social proof type and placement, CTA copy/placement/number, form length, default selections (plan, billing period), visual hierarchy. Change one meaningful thing, boldly.

## 3. Attribution views

No single model is right. Report several and say which decision each serves.

| View | Answers | Weakness |
|---|---|---|
| Last non-direct click | Which channel closes | Undervalues discovery channels |
| First touch | What creates demand | Ignores nurturing |
| Position/data-driven (multi-touch) | Shared credit | Only sees trackable touches; opaque |
| Self-reported ("How did you hear about us?" free text at signup) | Dark social, podcasts, word of mouth | Recall bias; needs coding |
| Platform-reported | Bid optimization input | Overlapping claims; sum > reality |
| Incrementality (geo or audience holdout) | True causal lift | Needs spend scale and time |
| Media mix model | Budget allocation across channels | Needs 2+ years of weekly data |

Rules: keep the order table as ground truth; compare platform claims to it as a ratio; when budgets are large or a channel looks too good, run a holdout before scaling. Report ranges, not false precision.

## 4. Analytics tool setup (GA4-style property and tag manager)

**Property basics**
- One property per product, one data stream per platform (web, iOS, Android).
- Turn on enhanced measurement (page views, scroll at 90%, outbound clicks, site search, video, file downloads), then disable anything you re-implement yourself to avoid duplicates.
- Data retention: raise from the 2-month default to the maximum (14 months) on day one; it is not retroactive.
- Define internal traffic (office IPs, staff) and developer traffic filters; list all your domains for cross-domain measurement; leave session timeout at 30 min unless you have a reason.
- Custom definitions: event-scoped (content_type), user-scoped (plan_type), item-scoped (item_category). The parameter name must match exactly; data appears only from creation onward, with 24-48 h processing lag.
- Key events/conversions: mark only outcomes; counting "once per session" for leads, "every event" for purchases. Link the ads account and import key events for bidding.
- Audiences for remarketing and analysis: high intent (viewed pricing, no conversion, last 7 days), engaged (3+ sessions), purchasers (exclusion lists, lookalike seeds).

**Recommended event names** (use instead of inventing): `login`, `sign_up`, `search`, `share`, `view_item`, `view_item_list`, `add_to_cart`, `remove_from_cart`, `begin_checkout`, `add_payment_info`, `add_shipping_info`, `purchase`, `refund`, `generate_lead`.

**Code shape**
```js
// direct tag
gtag('event', 'sign_up', { method: 'google', plan: 'free' });
gtag('set', 'user_properties', { plan_type: 'pro' });
// tag manager data layer: clear the ecommerce object before each ecommerce push
window.dataLayer = window.dataLayer || [];
dataLayer.push({ ecommerce: null });
dataLayer.push({ event: 'purchase', ecommerce: {
  transaction_id: 'T-10293', value: 49.0, currency: 'USD', tax: 0, shipping: 0,
  items: [{ item_id: 'pro-monthly', item_name: 'Pro', price: 49.0, quantity: 1 }] } });
```

**Tag manager conventions**
- Names: `[Tool] - [Type] - [What]` for tags (`GA4 - Event - Sign Up`), `[Trigger type] - [What]` for triggers (`Custom - sign_up`, `Click - Hero CTA`), prefix variables by kind (`DL - plan`, `JS - timestamp`, `LT - source map`).
- Prefer custom-event triggers from the data layer over CSS-selector click triggers; selectors break on redesign.
- Use workspaces, describe every published version, and keep the previous version to roll back.
- Sequence base/config tags before event tags; add exception triggers for internal traffic and staging hosts.
- Wire consent: tags declare required consent types; default denied in consent regions.

## 5. UTMs

| Parameter | Use | Allowed values |
|---|---|---|
| `utm_source` | Who sent it | `google`, `meta`, `linkedin`, `newsletter`, `partner-acme` |
| `utm_medium` | Channel type (fixed list) | `cpc`, `paid-social`, `display`, `email`, `social`, `referral`, `affiliate`, `sms`, `podcast` |
| `utm_campaign` | Campaign | `2026-q4-launch-ai-reports` |
| `utm_content` | Creative/placement | `hero-video-a`, `footer-link` |
| `utm_term` | Keyword or audience | `crm+for+startups`, `lal-1pct-buyers` |

Rules: lowercase; hyphens inside values; fixed `utm_medium` vocabulary (map to the analytics tool's default channel groups or traffic lands in "Unassigned"); every link logged in a shared sheet with owner and date; never tag internal links; keep auto-tagging (click ids) on for ad platforms in addition to UTMs; shorten tagged links only with redirects that preserve the query string.

## 6. Server-side conversion reporting

**Click id parameters**: Meta `fbclid` (plus `_fbp`/`_fbc` cookies), Google `gclid` (`wbraid`/`gbraid` on iOS), TikTok `ttclid`, Bing `msclkid`, LinkedIn `li_fat_id`.

**Endpoints (generic)**: Meta Conversions API (pixel id + token); TikTok Events API (pixel code + token); Google Ads offline/enhanced conversion import keyed by click id or hashed email; Bing offline conversions / conversions API; LinkedIn Conversions API.

**Payload per event**: event name, event time (Unix seconds, when it actually happened), `event_id` (same as the browser event), action source (`website`), event source URL, value, currency, click id, `client_ip_address` and `client_user_agent` of the visitor (from forwarded headers behind a proxy/CDN, never your server's), hashed email/phone/name/city/zip where consented.

**Normalization before SHA-256**: trim, lowercase; email as-is after that; phone digits only in E.164 with country code (`+919812345678` → hash of `919812345678` or the form the platform specifies); names lowercase without punctuation; zip first 5 (US). Wrong normalization silently drops match rate.

**Operational rules**: queue + retries with backoff; idempotent on `event_id`; send within the platform's freshness window (commonly ≤ 7 days, sooner is better); Meta only deduplicates a browser and server event with the same `event_name` + `event_id` if the second arrives within 48 hours of the first; log responses; alert when daily sent events deviate > 30% from orders.

**What it does not fix**: it does not restore cross-site user tracking, does not make platforms agree (sum of claims > orders), and does not override consent. Hashed PII is still PII.

**Verification**: platform test-event console (arrival + match quality); click-id coverage on paid orders; weekly orders-vs-platform ratio; compare on 7+ day windows because platforms attribute to click date while your database uses order date.

## 7. Consent and privacy

- EU/UK (and similar regimes): no non-essential cookies or pixels before consent; consent mode with default denied; regional defaults for others. Google Consent Mode v2 (required for EEA/UK ad measurement and remarketing since March 2024) sends four signals: `ad_storage`, `analytics_storage`, `ad_user_data`, `ad_personalization`. Basic mode loads no tags until consent; advanced mode sends cookieless pings for modelling. Google requires a Google-certified CMP for EEA/UK/Swiss traffic on its publisher products.
- Server-side to Google: the GA4 Measurement Protocol is in maintenance mode (2026); Google points new server-side ingestion to the Data Manager API. Check current docs before building a new integration.
- Other regimes: India's DPDP Act 2023 needs notice and consent for personal data; Brazil's LGPD and US state laws (e.g. CCPA/CPRA opt-out of sale/share) also apply.
- Never put PII in analytics events, page titles or URLs; scrub query strings like `email=`.
- Set retention, honor deletion requests (user-id based deletion), document processors.
- IP truncation is automatic in some tools; confirm.
- Server-side sending still needs a lawful basis and the user's consent choice respected.

## 8. Debugging matrix

| Symptom | Check first | Then |
|---|---|---|
| Event never appears | Debug view / tag preview: did the trigger fire? | Consent state, ad blocker, tag paused, wrong container on page |
| Event fires twice | Two containers or both direct tag and tag manager | Trigger on both click and submit; SPA route change firing page view twice |
| Parameter blank in reports | Custom definition missing or misspelled | Processing lag (24-48 h), thresholding on small numbers |
| Conversions far below orders | Counting method, key event marked? | Consent opt-outs, redirect to third-party checkout dropping session, payment page cross-domain not listed |
| Traffic "Unassigned"/"(other)" | Nonstandard `utm_medium` | Missing source on email links, internal UTMs |
| Self-referrals from payment provider | Add to referral exclusion list | Cross-domain configuration |
| Platform claims > orders | Normal overlap | Look at ratio stability, dedupe `event_id` |
| Test arm counts uneven | SRM check | Redirect latency, bots, caching of one variant |
